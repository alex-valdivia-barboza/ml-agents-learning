LECCIÓN 2.6 · FUNDAMENTO Tool use

Errores como información

Cuando el agente pide algo imposible (moverse contra una pared), el programa no se detiene: le devuelve el error como un resultado más, marcado con is_error, y el modelo corrige. El caso real de la corrida y un caso donde corregir no alcanza.

1. El código

12_agent_with_llm.py · líneas 175–181
try:
    salida = ejecutar_herramienta(entorno, pedido.name, pedido.input)
    resultados.append({"type": "tool_result", "tool_use_id": pedido.id, "content": salida})
except ValueError as error:                       # el error vuelve como información
    errores += 1
    resultados.append({"type": "tool_result", "tool_use_id": pedido.id,
                       "content": f"Error: {error}", "is_error": True})

Entorno.mover lanza un ValueError con un mensaje que explica qué pasó (línea 82: “no se puede mover abajo desde (0, 1): hay pared o borde”). try / except lo atrapa y lo convierte en un tool_result con "is_error": True.

  • Si no se atrapara, el programa terminaría con un error y el agente quedaría a mitad de camino.
  • Si se descartara en silencio, el modelo creería que se movió y su idea de dónde está quedaría equivocada.
  • Devuelto como resultado, el modelo se entera, y puede razonar sobre por qué falló.

Por eso el mensaje de error es tan importante como el de éxito: tiene que decir qué salió mal en palabras que ayuden a corregir. “Error 3” no le sirve a nadie; “hay pared o borde” sí.

2. En la corrida

  limpiar({}) -> Celda (0, 1) limpia. Quedan 4 sucias.
  mover({"direccion": "abajo"}) -> Error: no se puede mover abajo desde (0, 1): hay pared o borde
  mover({"direccion": "derecha"}) -> Ahora en (0, 2). La celda esta limpia.
  mover({"direccion": "abajo"}) -> Ahora en (1, 2). La celda esta sucia.

El simulado quería llegar a (1, 2) y probó bajar primero; había pared. Con el error, cambió de eje: fue a la derecha y después bajó. Costó una llamada al modelo de más, pero ninguna acción (un movimiento fallido no gasta acción en este entorno).

3. Cuando corregir no alcanza

El simulado no planifica: va en línea recta y, si choca, prueba el otro eje. Con un mapa con una pared larga, eso no sirve:

  mover({"direccion": "abajo"}) -> Error: no se puede mover abajo desde (0, 0): hay pared o borde
  mover({"direccion": "izquierda"}) -> Error: no se puede mover izquierda desde (0, 0): hay pared o borde
  mover({"direccion": "abajo"}) -> Error: ...
  ...

Resultado real: 60 llamadas (el tope max_vueltas), 54 errores, 3 celdas sucias sin limpiar. El BFS resuelve ese mismo mapa en 18 acciones. El error le dio la información, pero su estrategia no sabía usarla: la salida estaba a la derecha, rodeando la pared.

Lo que aporta un LLM real: Claude recibe el mapa completo como texto y puede razonar “la pared cubre toda la fila 1 salvo la última columna: tengo que ir por la derecha”. Un LLM no es un algoritmo de búsqueda, pero sí puede planificar un recorrido a partir de una descripción. Ese es el valor del modelo frente a una regla fija como la del simulado. Y, de todos modos, el tope de vueltas hace falta: un modelo también puede insistir en algo que no funciona.
